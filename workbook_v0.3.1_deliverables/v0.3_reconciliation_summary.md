## 4. Verification method (why this counts as "run")
No tool in this session can write cells into an existing Google Sheet
(Drive access here is whole-file only: search/read/copy/create/download).
Formula correctness was verified two ways, and one open-source
verification-tool limitation was found and root-caused:

1. **Structural/formula-text validation at full production scale.**
   Every generated formula in every touched (sheet, column, row) was
   compared against what an Excel/Sheets fill-down would produce, using a
   translator validated against the workbook's own pre-existing 6->845
   pattern (15/15 exact matches), then spot-checked across 1,140+ cells
   with zero mismatches after the row-845 self-reference bug fix. A
   full-workbook cell-by-cell diff against the untouched v0.2.2 confirmed
   zero changes outside the documented zones.

2. **Live formula calculation via the open-source `formulas` Python
   engine**, on a compact scratch workbook built from the *exact same*
   real v0.2.2 formulas and the *exact same* extension code (just scaled
   from a 14-row to a 20-row boundary instead of 845->1005, to fit the
   engine's practical size limits). Confirmed by live calculation:
   - FBS v FBS (UNC at TCU): both sides classify FBS.
   - FBS v FCS (Bethune-Cookman at UCF): away correctly falls through to
     FCS (no alias match + conference string not in the FBS list); home
     stays FBS.
   - Neutral site (UNC at TCU, neutral=TRUE): ENGINE HFA = 0 exactly.
     Every non-neutral test row: HFA = 2.5 (SETTINGS default).
   - North Dakota State: resolves to abbrev NDSU, type FBS.
   - Sacramento State: resolves to abbrev SAC, type FBS.
   - Miami Hurricanes -> MIA; Miami (OH) RedHawks -> M-OH (distinct,
     never conflated).
   - A game placed at row 18 (beyond the scaled-down old boundary of 14)
     flowed correctly through CLEAN (classified FBS v FBS) exactly like
     rows 6-14, proving the extension mechanism.
   - A deliberately duplicated GameID (two rows, same id) produced
     CLEAN!dup-count = 2 on both rows, and ENGINE's block-reasons column
     correctly appended "DUP GAMEID;" on both — the per-row detection
     that AUDIT's aggregate check consumes.
   - **One discrepancy found and root-caused:** AUDIT/DATA QUALITY's
     `SUMPRODUCT(--(range<>""),--(range>1))`-style aggregate checks did not
     reflect the duplicate correctly in this third-party engine. Isolated
     in a standalone 8-cell probe workbook: the `--` (double-unary-negate)
     idiom over a range containing blanks returns 0 in this library, while
     the mathematically identical `*`-based version of the same formula
     returns the correct value (2) on identical data. This is a documented
     limitation of the open-source `formulas` package, not a defect in the
     workbook — the formula text itself is untouched original v0.2.2
     logic, a standard Excel/Sheets idiom that a real Sheets recalculation
     evaluates correctly. Per-row detection (which does not depend on
     SUMPRODUCT) is proven correct above.

3. **Structural confirmation of production end-state** (via direct file

## 6. v0.3.1 corrections

### 6.1 IMPORT SCHEDULE physical row extension
v0.3 extended every *downstream* game-pipeline sheet to row 1005, but never
touched IMPORT SCHEDULE's own dimensions — it had no formulas there to
trigger the extension logic, so the sheet's own used range stayed at
`A1:N1000` even though CLEAN/ENGINE already read through row 1005. Fixed:
rows 1001-1005 (A:N) now physically exist, styled to match the existing
blank paste-zone (row 1000). Confirmed: `ws.dimensions` reads `A1:N1005`
after the fix. Verified via live calculation (compact scratch model, exact
same formulas) that a game placed at the scratch model's equivalent of
production row 1005 flows correctly through CLEAN (team/conference
classification), ENGINE (status, block reasons), and DATA QUALITY (games
loaded / BLOCKED counters) — see `extended_ranges_summary.md` Section 5 for
the full trace.

### 6.2 start_date converted to native dates
v0.3 loaded `start_date` as literal ISO text (`'2026-08-29'`, a Python
`str`). Converted all 888 values to native date objects, format
`yyyy-mm-dd`. Verified lossless: every converted date's ISO string was
re-compared against the original CSV text for all 888 rows — 0 mismatches.
Week 0 (2026-08-29, 2026-08-30 — 8 rows) and the Week 1 start
(2026-09-03) are unaffected, because week routing is driven by IMPORT
SCHEDULE column C (`week`, already a plain integer, untouched), not by the
date column's type. The `yyyy-mm-dd` format was also pre-applied to the
rest of column D (rows 894-1005) so future manually-pasted dates display
correctly without an extra formatting step.

### 6.3 ENGINE!AL846:AL1005 Notes-input formatting restored
ENGINE!AL is the one manually-edited column on that tab (Notes input,
yellow fill). v0.3's row-extension loop only copied a column's style
*alongside* copying its formula; since AL has no formula (it's pure user
input), it was silently skipped for the new rows 846-1005, leaving them
unstyled. Fixed: AL846:AL1005 now carries the exact same fill/font/border/
alignment/number-format/protection as AL845. No formula was written to AL
— it remains manual-entry only, matching AL6:AL845.

### 6.4 Scope of the fix
A full cell-by-cell diff of v0.3.1 against v0.3 shows changes in exactly
four sheets and nothing else: START HERE (1 cell, version banner),
CHANGELOG (12 cells, 3 new rows), ENGINE (160 cells, AL846:AL1005 style
only), IMPORT SCHEDULE (the D column across rows 6-1005, plus rows
1001-1005 now physically present). TEAM MAP, CLEAN, DASHBOARD, MARKET
LINES, CALC, TEAM RATINGS, QB VALUES, AUDIT, DATA QUALITY, SETTINGS,
ADJUSTMENTS, PRESEASON, FCS TIERS, IMPORT STATS, HISTORY, BACKTEST,
DICTIONARY: unchanged.

## 7. Delivery constraint
This session's Drive connector exposes whole-file operations only
(search / read / copy / create / download) — there is no cell-level write
API to edit the live v0.2.2 Sheet or push data into a new Sheet
incrementally. Creating a new Drive file requires inlining its full
content as base64 in the tool call; the production workbook (~2.46 MB)
is far past what fits in available context for that path (a 180KB test
file already exceeded the 256KB file-read ceiling needed just to stage
it). The finished workbook is delivered directly as a file instead of
being placed into Drive automatically; uploading it to Drive is a
30-second manual "File > Import" step.
